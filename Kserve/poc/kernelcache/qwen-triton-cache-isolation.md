# POC-2: Qwen Triton Cache Isolation Verification

### Goal

Verify whether the Triton cache entries newly generated by `Qwen/Qwen2.5-0.5B` are sufficient to reuse the Qwen AOT cache without depending on Triton cache entries previously generated by `facebook/opt-125m`.

### Test Setup

Two PVCs were mounted separately:

```text
/tmp/vllm   -> VLLM_CACHE_ROOT
/tmp/triton -> TRITON_CACHE_DIR
```

The existing `/tmp/vllm` cache was kept unchanged.

For `/tmp/triton`, only the **21 Triton cache entries newly generated by Qwen** were retained. The 30 entries previously generated by OPT were removed from the test set.

### Result

Qwen started successfully and reused the existing AOT artifact:

```text
reconstructed serializable fn from standalone compile artifacts
Directly load AOT compilation from path
/tmp/vllm/torch_compile_cache/torch_aot_compile/2e255240773e1183b2e0bf6e294532c36b76dc5251c58e2949ccd9d781bcfca0/rank_0_0/model
```

Observed startup timing:

```text
torch.compile took 0.36 s in total
init engine ... took 7.99 s (compilation: 0.36 s)
```

No Triton cubin reload failures were observed:

```text
Failed to reload cubin
```

was not present in the logs.

A real inference request was also executed successfully:

```text
POST /v1/completions HTTP/1.1" 200 OK
```

No additional JIT compilation warnings were observed after the inference request.

### Conclusion

For this Qwen workload, the **21 Triton cache entries generated during the Qwen run were sufficient for both startup and inference**.

The Qwen AOT artifact did not require the Triton cache entries previously generated by the OPT workload.

This provides evidence that Triton cache artifacts can be isolated as workload-specific deltas rather than requiring the entire shared `TRITON_CACHE_DIR` to be captured.

> This result is specific to the tested workload and configuration. Additional verification is required before assuming that cache deltas are always independently portable across models or configurations.
